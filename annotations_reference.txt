Spring Boot Annotations Reference Guide
=======================================

This file contains a list of commonly used Spring Boot and Java annotations, along with their definitions and use cases.

@RequestBody
- Purpose: Maps the incoming HTTP request body (usually JSON) to a Java object.
- Usage: Placed in the method parameters of a controller (often with POST or PUT requests). It tells Spring to convert the incoming JSON into the specified Java class.

@Valid
- Purpose: Triggers validation on a Java object before the method executes.
- Usage: Placed next to @RequestBody. It checks the fields of the object against validation annotations (like @NotNull, @NotBlank) defined inside the DTO class. If validation fails, it throws an error before running the method.

@RestController
- Purpose: Marks a class as a RESTful web controller. It is a convenience annotation that combines @Controller and @ResponseBody, meaning the returned data is written directly to the HTTP response as JSON/XML, rather than rendering a HTML page.

@RequestMapping
- Purpose: Used to map web requests onto specific handler classes and/or handler methods. For example, @RequestMapping("/students") at the class level means all endpoints in that controller start with "/students".

@GetMapping / @PostMapping / @PutMapping / @DeleteMapping / @PatchMapping
- Purpose: These are shortcut annotations for @RequestMapping with specific HTTP methods (GET, POST, PUT, DELETE, PATCH).

@PathVariable
- Purpose: Extracts values from the URI path. For example, for an endpoint "/students/{id}", you use @PathVariable Long id to grab the "id" from the URL.

@RequiredArgsConstructor (from Lombok)
- Purpose: Automatically generates a constructor that takes one argument for every final field. In Spring Boot, this is a very clean way to do Constructor Dependency Injection (e.g., injecting your StudentService into your StudentController) without writing boilerplate constructors.




The 3 Layers of Spring Boot
Before tracing the flow, here is a quick reminder of what your three main layers do:

Controller Layer (StudentController): The receptionist. It receives HTTP requests, validates them, and hands them off to the Service.
Service Layer (StudentService): The brain. It contains your business logic, performs calculations, and decides what to do with the data.
Repository Layer (StudentRepository): The filing cabinet. It only cares about talking to the database (saving, fetching, deleting data).
The Complete Journey (Step-by-Step Flow)
PHASE 1: The Inward Journey (Client ➔ Database)
1. The Client Sends JSON (The Request) A frontend app (or Postman) sends an HTTP POST request to /students with this JSON body:

json
{
  "name": "John Doe",
  "email": "john@example.com"
}
2. The Controller Receives the Request (@RequestBody) The request hits StudentController.java. Because you used @RequestBody, a built-in Spring tool (called Jackson) automatically intercepts that JSON text and converts (deserializes) it into your Java AddStudentRequestDto object.

Current State: You now have an AddStudentRequestDto in your Controller.
3. The Controller calls the Service The Controller doesn't know how to save things to a database. It just says, "Hey Service, create a student using this DTO!" and passes the AddStudentRequestDto to StudentServiceImpl.java.

4. The Service Maps DTO to Entity (ModelMapper) The Service knows it needs to save data using the Repository, but the Repository only accepts Entities (the Student class). So, the Service uses ModelMapper to copy the data from your AddStudentRequestDto into a brand new Student entity.

Current State: You now have a Student entity.
5. The Repository Saves to Database The Service passes the Student entity to StudentRepository.save(). Spring Data JPA translates this into a SQL INSERT statement and runs it on your database. The database generates an ID (e.g., id: 1) and returns the saved entity back to the Service.

PHASE 2: The Outward Journey (Database ➔ Client)
6. The Service Maps Entity back to DTO (ModelMapper) The Service now has the saved Student entity (complete with its new database ID). However, it is a bad practice to return database entities back to the Controller. So, the Service uses ModelMapper again to copy the data from the Student entity into a StudentDto.

Current State: You now have a StudentDto.
7. The Service returns the DTO to the Controller The Service hands the StudentDto back to the Controller.

8. The Controller returns the Response (@RestController) The Controller takes the StudentDto and wraps it in a ResponseEntity with a 201 Created status code. Because your class is annotated with @RestController (which secretly includes @ResponseBody), Spring Boot's Jackson tool jumps in one last time. It takes your StudentDto and automatically converts (serializes) it back into a JSON text string.

9. The Client Receives the JSON The frontend receives the HTTP response:

Status: 201 Created
Body:
json
{
  "id": 1,
  "name": "John Doe",
  "email": "john@example.com"
}
